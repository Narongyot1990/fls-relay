# Inventory and driver lifecycle — 9 November 2026

Applies to `/preview`, which is also the destination of `/`. Uses the supplied
`Driver_Phone_Issuing__Return_Process.pdf` as the workflow reference. The supplied
Claude artifact was inaccessible during implementation.

- **Devices:** Total, In stock and Assigned are filter buttons. Search combines
  with the selected status; totals continue to describe the selected site scope.
  In stock includes registered central stock and in-site stock; damaged and
  pending transfers are excluded.
- **Issue:** Driver rows distinguish Has phone / No phone using text, color and
  icons. Toggle All drivers / Has phone / No phone, or open the information icon
  for model, Device ID, phone number, IMEI and serial. Existing assignments show
  a warning before an additional issue; multiple phones per driver remain allowed.
  Central Stock can select drivers at their actual sites and still see their
  existing assignments. Issuable-device selection matches the API state rules.
- **Return:** Assigned drivers appear immediately, including inactive drivers who
  still hold a phone. If a driver has multiple phones, choose the exact device.
  Record OK or damaged condition and optional notes. Damaged phones remain blocked
  from issue.
- **Recall:** Open Return and choose Recall phone. IT and System Admin open directly
  in recall mode; Implementation and Site Leaders can switch modes. A nonblank
  reason of at most 1,000 characters is required and retained in history. Confirm
  only after physically receiving the phone; this operation closes the assignment,
  rather than creating a future collection request. Site Leaders remain restricted
  to their assigned site. Central roles can recall across sites. This does not grant
  IT or System Admin ordinary issue/exchange permission.
- **Exchange:** Select assigned driver/device, return condition and replacement,
  then present the full agreement and collect a new driver signature and
  acknowledgement. Returning the old phone, assigning the replacement and writing
  both linked history entries commit in a single MongoDB transaction. Issue and
  return also commit their device changes and audit entry together. Requires a
  replica set or sharded MongoDB deployment; topology was checked read-only.
- **Signer:** The signature block explicitly identifies the driver as receipt
  signer and the Site Leader as issuing operator. APIs derive and persist signer
  ID and name from the selected driver record, separately from the acting operator.
  Historical records without a signer snapshot fall back to the recipient name.
- **History:** Collapsible groups per phone show its model and Device ID, relative
  last transaction time (`1min`, `1h`, `1d`, `1week`) and absolute
  `dd/mmm/yyyy hh:mm` in Asia/Bangkok. Expanded entries include parties, condition,
  reason, signer, transaction ID and linked exchange reference. Search covers
  loaded records; Load more history fetches the next 200 entries.

Validation uses `npm run test:inventory` and `npm run test:ui`; all write tests
use in-memory database fakes or intercepted API requests. Browser tests cover
mobile/desktop filters, Thai labels, assignment toggles/details, all four recall
roles, multiple assigned phones, replacement signatures and collapsible history.
No inventory was seeded or changed during verification.

Existing boundaries: the public role switcher remains a workflow testing tool,
not authentication. Signature evidence is stored with transactions, but downloadable
handover PDFs are not generated by this change. No deployment is performed.
